# 架构方案多角度论辩（正反方对垒）

> 日期: 2026-10-05
> 前置: 《ARCHITECTURE_REVIEW_v33.md》提出了"三步走"重构规划。
> 本文从 6 个立场对该规划逐条攻击与辩护,最后给出裁决与具体做法。
> 原则: 每个反方论点必须被正面回应,不许和稀泥。

## 争议点一: 巨石文件 main(4494行) 要不要拆?

### 🔴 正方(拆):
- 本次排错实证: `COMM` 变量遮蔽排查40分钟; 两个相邻 `_stratagem_block` 定义静默覆盖; 死文件没人敢删。**巨石的直接成本已经付过一次了**
- 1500行 main() 意味着任何改动都要理解全文才能确认无副作用, 新功能(36计)接入点找半天
- 测试无法落地: 类之间靠模块级 global 缝合, 单测无从下手

### 🔵 反方(不拆):
- **它能跑**。30fps、几百实体、6路LLM, 全部工作正常。拆文件是为了人, 不是为了机器——而用户只有一个人, 改动者只有 AI+用户, 沟通成本未必比现在高
- 拆文件的历史风险远大于收益: 逐类搬迁过程中 import 路径、循环依赖、pickle/引用断裂, 每一步都可能引入"本次排错清单"级别的新 bug
- 283代进化数据、实战验证的时序(pending锁/遥测帧对齐)全都埋在这个文件的语句顺序里。**搬动语句顺序 = 重掷骰子**

### ⚖️ 裁决: **有限度拆, 但不做"目录级重组"**
反方说得对的部分: 不要 `engine/ ai/ infra/` 大搬家。正方成立的部分: 巨石确实已经在伤人。

**具体做法(折中案)**:
1. main() 里**只拆出三个纯函数块**到新文件, 用最保守的方式:
   - `world_api.py`: `separate_enemies/barricade_*` 等 4 个纯几何函数(零依赖, 搬走零风险)
   - `channels.py`: `WeiCommandChannel/AdvisorChannel/SquadComm` 三个通讯类(它们互相独立, 且本次已经因跨文件访问踩过坑, 集中后 `attach_channel` 模式可统一)
   - `directors.py`: `AIDirector/ClusterPlanner/BattleMemory/FormationManager`(一个 import 即得, 游戏主文件只留 `from directors import AIDirector`)
2. **保留** main()/实体类(Bullet/Tank/Player/Enemy/General/Boss)在原文件——它们与 pygame 主循环语句顺序强耦合, 是反方警告的"重掷骰子"区
3. 每搬一个文件跑一次无头冒烟(已有成熟流程, 3遍×25s), 当天完成
4. 结果: 主文件 4494→约2600行, 新增3个各300-600行的内聚类。**不做目录树, 不改 import 风格**

## 争议点二: 四套战术存储合一, 值不值得?

### 🔴 正方(合一):
- 量化实锤(刚刚从两个存档里挖出来的真实数据):
  - `tactics_db.json`: 直攻 used=448, hits=1278, deaths=0
  - `evolution.json plan_stats`: 直攻 issued=2084, hits=2533, deaths=137
  - **同一战术, 两套账, 数字差4.6倍, 一边deaths=0一边deaths=137**
- 这不是脏数据, 是**语义不同却长得一样**: tactics_db 记"子弹命中时该敌当时挂的战术", plan_stats 记"发令时记账"。两个口径都有价值, 但并存且同名 = 给LLM看A账、进化吃B账, 复盘结论建立在错位数据上
- 已造成实际伤害: 提示词里"直攻: 使用448次效果0.44"和复盘里"直攻发令2084次"同时喂给LLM, 它自己都精神分裂

### 🔵 反方(不合):
- 两个口径本来就是**两种度量**(命中视角 vs 发令视角), 强行合一要么丢信息要么加字段区分
- plan_stats 在 AIDirector 内存里高频写, 硬拽到 hsdb 等于把每1.5s一次的记账变成跨模块调用, 引入新的锁竞争
- "数字对不上"对LLM无害——它不会做账, 它只看趋势

### ⚖️ 裁决: **不合并存储, 合并"出口"** — 反方对存储, 正方对展示
**具体做法**:
1. 存储保持两套(口径不同, 各有价值), 但:
   - `tactics_db.json` 改名为语义明确的 `tactics_hit_account.json`(命中视角账本)
   - plan_stats 保持内存+进化存档(发令视角账本)
2. **新增唯一出口** `stats_view.py`: 提供 `get_tactic_report()` 把两套账并排换算后输出(发令/命中/命中/发令比、双口径效果分), 提示词里只喂这一份合并视图
3. 一行注释写死两个口径的定义, 埋在两个文件头部
4. 工作量: 半天。收益: LLM看到的数字从此自洽, 复盘不再基于错位数据

## 争议点三: R重开递归 → 软复位, 现在做还是永远不做?

### 🔴 正方(现在做):
- 每重开一次泄漏: 3×AIDirector(各含BattleMemory行为模型字典)+SquadComm+11个daemon线程的闭包引用+AdvisorChannel会话历史。R十次 = 内存里挂十个僵尸军团
- 已经有现成的补丁范式: UDP那组"模块级单例+global"就是为递归问题打的补丁——**说明作者已经踩过一次, 补丁只补了socket一个洞**

### 🔵 反方(缓做):
- 玩家一局被打死几次? R重开频率极低, 泄漏速率=每局几百KB, 一晚上挂机重开50次也就几十MB, 32GB内存毫无压力
- 软复位要枚举**所有**需要清零的状态(实体组/波次/技能CD/频道历史/进化缓冲/遥测计数器/选计器), 漏一个就是"第二局开局敌人自带上一局残血"这类诡异bug——**比泄漏可怕得多**

### ⚖️ 裁决: **做, 但用"进程自杀重启"而不是"手工清零"** — 两方优点全拿
**具体做法(取巧方案)**:
1. R重开时不再递归调用 main(), 改为:
   ```python
   if state in ("gameover", "win") and event.key == pygame.K_r:
       os.execv(sys.executable, [sys.executable] + sys.argv)  # 进程重生
   ```
2. 进程级重启 = 内核兜底清零一切(线程/内存/socket), **不存在漏清状态的可能**——反方"漏清比泄漏可怕"的论点被物理消灭
3. 代价: 重开耗时+3秒(python启动+LLM握手), 对"按下R"这个场景完全可接受
4. LLM服务/进化存档都在游戏进程外或磁盘上, 不受影响
5. 工作量: 5行代码。风险: 低于递归方案

## 争议点四: 吞异常(except:pass)统一留痕, 会不会把日志炸了?

### 🔴 正方(留痕):
- 本次7个bug中3个(SQLite跨线程/urllib/网络时序)全靠"猜"才定位, 若当时有一行 swallow 日志, 每个5分钟就能抓到
- `except: pass` 的真实成本不是现在, 是三个月后的某次"游戏莫名功能失效"

### 🔵 反方(现状即合理):
- 游戏是30fps实时循环, LLM服务时有时无、文件时序竞争是常态, 若每次连接拒绝都留痕, 一晚上 `/tmp` 里几万行废话, 反而淹掉真信号
- "每位置每小时限1条"听起来美, 但21处都要手工加 try/except 改造, 改错一处缩进就是新bug

### ⚖️ 裁决: **做, 但用装饰器自动包, 不手工改21处**
**具体做法**:
1. 新增 `infra/swallow.py`(或直接塞logger.py):
   ```python
   _last_report = {}
   def swallow(tag, exc, rate=3600):
       now = time.time()
       if now - _last_report.get(tag, 0) < rate: return
       _last_report[tag] = now
       print(f"[SWALLOWED] {tag}: {type(exc).__name__}: {exc}", flush=True)
   ```
2. 不逐处改 try/except 结构(反方风险成立), **只改"值得监控"的8处**: 数据落盘/进化/选计/遥测写盘——这些是"静默失效会伤功能"的; 纯防御性的(遥测读不到文件等)保持 pass
3. 每小时每标签1条, 一晚上日志增量 <100行, 反方的日志爆炸论不成立
4. 工作量: 1小时

## 争议点五: LLM实例池(省一张卡)值不值得做?

### 🔴 正方(做):
- 现状: 同一个35B Q4模型加载4份, 3张卡各占~23GB(70%+)。llama-server 本身支持 `--parallel N` 和连续批处理, **一个实例就能服务多个并发请求**
- 省下的显存可以直接拉 ctx(现在军师只敢给8192, 因为要挤卡), 或给未来的第4帅/更大模型留位
- 4个端口4套配置, 运维时健康检查/重启/日志都是4倍工作量

### 🔵 反方(不做):
- 现状隔离=故障隔离: 三帅一个实例崩了, 军师还活着; 合池后单点故障全体失智
- llama-server 单实例多并发下, 长 prompt(三帅战术800-1000 token)和短 prompt(选计120 token)互相排队, 选计的8s超时可能被三帅的推理挤爆——**延迟确定性变差**
- 省卡的真实需求存疑: 又不缺卡(还有空闲槽), 省下来干嘛?

### ⚖️ 裁决: **不做合池, 做两个便宜的前置改进** — 反方的隔离论和延迟论都成立
**具体做法**:
1. `llm_client.py` 统一客户端(这个还是要做, 但**不**做池化): 5处调用点收敛, 自带重试/超时/降级/耗时统计, self_check 增加"LLM健康度"面板
2. 选计器 TIMEOUT 从8s提到12s, 并在 llm_client 里给短 prompt 加 `--priority` 语义(即: 选计失败立刻降级模板, 不重试; 三帅失败重试1次)——用策略分层替代资源合池
3. 第5个AI需求真出现时, 再评估合池。现在不做

## 争议点六: 回放/整局学习, 是真需求还是炫技?

### 🔴 正方(做):
- battle_recorder 已经在记完整帧(玩家/敌群/子弹/大营/事件), **数据已经在盘上了, 只差一个读回放的分析器**
- 现在进化只吃"波次摘要"(阵亡/受击计数), 整局的战术时序(方阵什么时候散的/集火充能被打断几次)全丢了。LLM复盘时"看不到过程只看结果", 教训质量有天花板

### 🔵 反方(缓做):
- 波次级进化已经实战跑了283代, 证明"结果数据+计数"对LLM够用——LLM本来就不擅长从时序回放里归纳, 喂它100帧JSON它只会复述
- 真正的整局学习瓶颈不在数据, 在**没人定义"整局好坏"的评分函数**。先有评分再谈回放, 顺序不能反

### ⚖️ 裁决: **做轻量版: 不做帧回放, 做"关键时刻时间线"** — 反方对LLM认知局限的判断成立
**具体做法**:
1. battle_recorder 的 `record_event()` 已存在但几乎没人调。在6个关键节点补埋点: 敌将出场/阵亡、方阵成阵/被破、集火充能完成/被打断、大营受击、玩家残血触发、计策切换
2. 波次复盘提示词里新增一段: `本波关键时刻: 12.3s方阵成阵(8台) → 18.1s被绕后击破 → 22.0s集火充能9/10失败`——给LLM的是**事件因果链**而非原始帧, 这才是它能消化的形态
3. 帧级数据继续落盘(未来想做什么都有原料), 但复盘只用时间线
4. 工作量: 埋点2小时+提示词1处

| 四套存储 | 合一 | 不合存储, 合展示出口(stats_view) | 半天 |

| 吞异常 | 21处全改 | 装饰器限流, 只改8处关键位 | 1小时 |
| LLM合池 | 第三步做 | 不做, 只做统一客户端+分层降级策略 | 半天 |
| 整局回放 | 回放分析器 | 只做关键时刻时间线埋点+复盘注入 | 3小时 |

**总工作量: 约3天, 全部可独立交付, 每步带无头冒烟验证。**

## 论辩后新增的共识(双方都同意的)

1. **283代进化数据和LLM分层架构是资产, 任何改动不得破坏其兼容性** — evolution.json 格式冻结
2. **游戏进程保持单进程** — 拆的是代码文件, 不是运行时
3. **每次改动后必须跑**: 三测试套件 + 无头3遍 + 数据落盘检查(本次的标准流程已成文档)
4. **evolution*.json 格式若将来要变**: 写迁移脚本, 不搞"新版本不认旧档"
